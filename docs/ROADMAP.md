# ROADMAP

ctfkit 개발 계획. 각 단계는 **통과 조건(Gate)** 을 만족해야 다음 단계로 넘어간다.
> 원칙: 미완성인 큰 프로젝트보다, 완성된 중간 규모 프로젝트가 낫다.
> Gate를 통과하지 못하면 다음 버전으로 가지 않고 현재 버전을 마무리한다.

- **마감:** 2026-12-06 (일) 23:59
- **현재:** v0.29.0 (2026-11-16 방향 재설정, 1주차 완료, 2주차 진행 중)

## 1. 방향 (2026-11-16 재설정)

**과제로 끝나는 도구가 아니라, 내가 CTF 에 나가서 실제로 쓰는 개인 작업 도구.**

실전에서 쓰는 개인 도구는 pwntools·CyberChef·Ghidra 를 대체하지 않는다. 그 도구들 **위에서** 매 문제마다
반복하는 일을 자동화한다. ctfkit 이 맡을 일은 세 가지다.

1. **문제를 받자마자 하는 일을 대신한다.** 폴더 만들기, 압축 풀기, 파일마다 형식·문자열·숨은 파일·보호 기법 확인,
   결과 기록. 어떤 문제든 처음 5~10분은 같은 일을 한다.
2. **자동으로 풀리는 문제는 자동으로 푼다.** 여러 겹 인코딩, 고전 암호, 약한 RSA, 파일 안에 숨긴 플래그.
   입문·중급 대회의 쉬운 문제는 여기서 끝난다.
3. **자동으로 안 풀리는 문제는 다음 걸음을 준비해 준다.** 분야에 맞는 풀이 스크립트 뼈대, 다음에 해 볼 명령,
   지금까지 한 일의 기록.

### 1.1 왜 방향을 바꾸는가

2026-11-16 에 `auto` 엔진을 CTF 에서 흔한 인코딩 22종으로 시험했더니 **6종만 풀었다**(2진수, 10진 코드, 모스 부호,
뒤집기, ROT47, 아트배시, 레일 펜스, HTML 엔티티, gzip+base64 등을 풀지 못함).
지금까지의 벤치마크는 "토큰을 얼마나 아끼는가" 만 쟀고 "문제를 얼마나 푸는가" 는 재지 않았다.
과제 14개는 ctfkit 이 풀 수 있는 것만 골라 만든 셈이라 약점이 수치에 드러나지 않았다.

| 아쉬운 점 | 원인 | 이번 방향에서의 처방 |
| --- | --- | --- |
| 성능 | 명령 13개가 모두 입문 수준 깊이. `auto` 가 아는 변환이 10종 | 해결률을 재고, 변환을 넓히고, 재귀 분석을 넣는다 |
| 활용도 | 실전 입력을 넣어 본 적이 없다. 다른 도구 대신 쓸 이유가 없다 | 문제 시작 자동화, 외부 도구 연결, 직접 풀면서 고치기 |
| 완성도 | 기능마다 다듬은 정도가 다르다 | 마지막 주를 마무리에만 쓴다 |

### 1.2 바꾸는 원칙 두 가지

| 원칙 | 이전 | 지금 | 이유 |
| --- | --- | --- | --- |
| 의존성 | 표준 라이브러리만. 무거운 것은 선택 의존성 | **표준 라이브러리로 기본 동작 + 설치된 외부 도구가 있으면 함께 쓴다** | binwalk·zsteg·exiftool·pwntools 는 이미 최고 수준이다. 순수 파이썬으로 다시 만들면 항상 뒤처진다 |
| 검증 | 직접 만든 예제로 테스트 | **직접 만든 예제 + 실제 문제를 풀며 막힌 지점 기록** | 한 번도 실전 입력을 넣지 않은 도구는 실전에서 깨진다 |

외부 도구는 **없어도 동작해야 한다.** 설치돼 있지 않으면 지금의 내장 구현으로 대신하고, 무엇을 설치하면 더 나은 결과가
나오는지 한 줄로 알려 준다. `pip install ctfkit` 만으로 쓸 수 있다는 점은 유지한다.

### 1.3 유지하는 것

- **구조:** 플러그인 레지스트리(변환 하나 = 파일 하나, 명령 하나 = 파일 하나), argparse 에서 자동 생성되는 그래픽 화면.
- **출력 규칙:** stdout 은 답, stderr 는 안내. `-q` 는 답만. 종료 코드 0 찾음 / 1 못 찾음 / 2 오류.
- **AI 에이전트가 쓰기 좋은 성질:** `guide`, `-q`, `triage`. 실전에서는 에이전트와 같이 푸는 경우가 많아 그대로 쓸모가 있다.
  다만 더는 프로젝트의 중심 주제가 아니다.
- **안전 범위:** `web` 은 허용 호스트 목록 밖으로 요청하지 않고 속도 제한을 둔다. `rev`·`pwn` 은 로컬 파일 정적 분석과
  풀이 스크립트 **초안 생성**까지만 한다. 원격 서비스에 대한 공격을 자동으로 실행하지 않는다.
- **AI API 를 직접 호출하지 않는다.**

### 1.4 하지 않는 것

| 하지 않는 것 | 이유 |
| --- | --- |
| 웹 공격 자동화 (sqlmap·ffuf 수준) | 기존 도구와 격차가 크고, 허가된 대상만 다룬다는 원칙상 깊이 들어가기 어렵다 |
| 디버거·디컴파일러 연동 (pwndbg, Ghidra) | 남은 기간에 의미 있는 수준에 닿지 못한다 |
| 해시 크래킹 강화 (hashcat, john 수준) | 순수 파이썬으로는 속도에서 비교가 되지 않는다. 설치돼 있으면 명령을 안내하는 데서 멈춘다 |
| 설명 모드, 그래픽 화면 추가 개선 | 실전 사용에 직접 도움이 되지 않는다 |
| 새 분야 추가 | 얕은 기능을 더 늘리면 같은 아쉬움이 반복된다 |

## 2. 측정

"좋아졌다" 는 세 가지 숫자로만 말한다.

| 측정 | 무엇을 재는가 | 어떻게 | 기록 위치 |
| --- | --- | --- | --- |
| **해결률** (새로 추가) | 자동 생성한 문제 중 `auto` 가 플래그까지 푸는 비율 | `python bench/solve.py` | `bench/SOLVE.md` |
| **실전 기록** (새로 추가) | 실제 문제를 풀 때 ctfkit 이 도운 것과 막힌 것 | 직접 풀면서 적는다 (아래 6절) | `docs/fieldlog.md` |
| 토큰·시간 (기존) | 직접 짠 코드 대비 비용 | `python bench/run.py` | `bench/RESULTS.md` |

### 2.1 해결률 벤치마크의 규칙

- **문제는 ctfkit 코드를 쓰지 않고 만든다.** 인코더를 벤치마크 안에 표준 라이브러리로 따로 구현한다.
  ctfkit 의 `encode` 로 만든 문제를 ctfkit 의 `decode` 로 풀면 같은 버그가 양쪽에 있어도 통과한다.
- **아직 지원하지 않는 인코딩도 넣는다.** 표에 X 로 남아야 무엇이 남았는지 보인다. 구현 계획이 없는 것(base45, base62,
  uuencode, 베이컨 암호, 아핀 암호 등)도 포함해 "천장" 을 정직하게 보여 준다.
- **한 겹, 두 겹, 세 겹을 따로 센다.** 겹이 늘면 탐색이 어려워진다.
- **플래그는 매번 무작위로 만든다.** 시드는 고정해 실행할 때마다 같은 문제가 나온다.
- **시간도 같이 잰다.** 변환을 늘려 해결률이 올라도 문제 하나에 몇 초씩 걸리면 쓸 수 없다.
- **벤치마크에 맞춰 도구를 고치지 않는다.** 특정 입력을 알아보는 처리를 넣지 않는다.

### 2.1.1 실제 문제 측정의 규칙 (11/24 추가)

실제 문제에서 못 푼 것을 고치고 같은 문제로 다시 재는 일이 반복됐다. 이것은 테스트 데이터로 학습하는 것과 같아서 수치가 부풀려진다.
그래서 실제 문제는 개발용(`bench/real/dev/`)과 평가용(`bench/real/eval/`)으로 나눈다 (`bench/README.md` 의 "측정 규칙").
평가용은 고치기 전에 보지 않고, 커밋한 상태로 한 번만 재며, README 의 대표 수치는 평가용 값만 쓴다.
지금까지 잰 드림핵 3문제는 측정 후 고쳤으므로 개발용이다.

#### v0.26 — 문제 시작 자동화 `ctfkit start` (~11/22) ✅ 11/16 완료

**만들 것**

```
ctfkit start chall.zip                  # 파일 하나
ctfkit start chall.zip --name web-100   # 작업 폴더 이름 지정
ctfkit start ./downloads/               # 폴더 통째로
```

한 번의 호출로 하는 일:

1. 작업 폴더를 만든다 (`workspace` 와 같은 구조: 노트, 명령 기록).
2. 원본을 `files/` 에 복사한다. 원본은 건드리지 않는다.
3. 압축 파일(zip, tar, gz)은 `extracted/` 에 푼다. 풀린 파일 안의 압축도 정해진 깊이까지 따라 들어간다.
4. 모든 파일에 `triage` 를 돌린다. 글자 파일은 `auto` 로 해독도 시도한다.
5. 결과를 화면에 요약하고 `notes.md` 에 적는다: 파일 목록, 형식, 찾은 플래그, 눈에 띄는 점, 다음에 해 볼 명령.

## 6. 직접 풀면서 기록하기

2주차부터 하루 한두 문제를 ctfkit 으로 푼다. 대상은 드림핵 워게임과 picoCTF 연습 문제.

문제마다 `docs/fieldlog.md` 에 다음을 적는다.

| 항목 | 내용 |
| --- | --- |
| 분야·난이도 | 예: 포렌식, 드림핵 1단계 |
| 처음 실행한 명령 | 보통 `ctfkit start` |
| ctfkit 이 한 것 | 자동으로 찾은 것, 줄여 준 단계 |
| 막힌 것 | 못 푼 인코딩, 틀린 출력, 불편했던 옵션, 없어서 다른 도구를 쓴 기능 |
| 다른 도구 | 무엇을 왜 썼는가 |
| 결과 | 풀었는가, 걸린 시간 |

- **플래그와 풀이 전문은 적지 않는다.** 저장소는 공개돼 있다. "어떤 형태의 입력에서 무엇이 안 됐는가" 만 적는다.
- "막힌 것" 이 곧 다음 작업 목록이다. 추측으로 기능을 만들지 않는다.

### 6.1 막힌 것을 고칠지 정하는 기준 (11/24 추가)

막힌 것을 하나씩 막는 방식은 끝이 없다. CTF 문제마다 고유한 트릭이 있기 때문이다. 그래서 고치기 전에 두 가지를 확인한다.

1. **그 문제를 말하지 않고 "어떤 종류의 문제를 푸는가" 를 한 줄로 쓸 수 있는가.** 예: "출력 파일에 hex 로 적은 바이트를 한 바이트 키로
   더하거나 XOR 한 문제". 못 쓰면 고치지 않고 실전 기록에 실패로만 남긴다.
2. **문제를 못 풀어도 비용을 줄이는 쪽을 먼저 본다.** 공격 소거, values.json, 소스 압축, 근거 출력은 트릭과 관계없이 에이전트의 왕복을
   줄인다. 자동 풀이는 실패하면 오히려 손해다 (실제 측정에서 못 푼 문제는 +3~15%).

지금까지 고친 것을 이 기준으로 다시 보면:

| 고친 것 | 한 줄 설명 | 일반성 |
| --- | --- | --- |
| 해독 깊이 4 → 6 | 여러 겹 인코딩 | 높음 |
| 반복 키 XOR, hex 속 한 바이트 키 | 짧은 키를 반복해 XOR·덧셈한 데이터 | 높음 |
| 자리 표시 플래그 무시, 바이너리 속 인코딩 조각 | 오탐 줄이기, 탐색 범위 | 높음 |
| 소스가 정한 알파벳의 다중 시저 | 표준이 아닌 알파벳으로 미는 비즈네르 | 중간 |
| 소스 상수 식 → RSA 소인수 후보 | 소스에 소수나 그 계산식을 적은 RSA | 중간 |
| `N1`·`FLAG1_enc` 번호로 쌍 짓기 | 여러 공개키로 나눠 암호화한 RSA | 중간 (이름 붙이는 방식에 기댐) |

- [x] 실행 기록 분석(`bench/agent_logs.py`, 11/24): 왕복이 비용을 정하고, 오류 난 호출의 대부분이 환경 문제(cp949, python3, strings)였다.
      에이전트는 start 출력을 읽고 AGENTS.md 를 또 열었다
- [x] AGENTS.md 에 "실행 환경" 절 (헛걸음하기 쉬운 것만, 리눅스 + UTF-8 이면 비어 있음)
- [x] 에이전트 모드: `CLAUDECODE`·`AI_AGENT`·`CTFKIT_AGENT=1` 이면 start 가 AGENTS.md 를 바로 출력 (보류했던 `CTFKIT_AGENT` 항목)
- [ ] 효과 측정은 평가용 문제로 (2.1.1). 남은 후보: 짧은 소스를 AGENTS.md 에 넣기, 풀이 뼈대 solve.py, 포렌식 "확인함: 없음" 기록,
      긴 출력을 파일로 빼기, start 가 플래그를 못 찾았을 때의 종료 코드 1 을 에이전트가 오류로 보는 문제(실제 문제 B 9번 중 8번)

## 7. 개발 방식

수업에서 강조한 "AI로 작성된 코드를 리뷰·수정·개선하는 개발"을 그대로 따른다.

1. **AI 작성:** 기능 단위로 AI(Claude Code)가 코드와 테스트를 작성한다.
2. **사람 리뷰:** 내가 코드를 읽고 이해한 뒤, 버그·설계 문제·이해 안 되는 부분을 리뷰로 남긴다.
3. **수정·개선 요청:** 리뷰 결과와 추가하고 싶은 기능을 AI에 요청하고, 반영된 결과를 다시 리뷰한다.
4. **측정:** 변경 전후로 `python bench/solve.py` 와 `python bench/run.py` 를 돌려 수치를 비교한다.
5. **직접 사용:** 실제 문제를 풀며 막힌 지점을 `docs/fieldlog.md` 에 적고, 그것을 다음 요청으로 삼는다.
6. **기록:** 매 사이클마다 devlog에 *요청한 것 / 리뷰에서 발견한 것 / 배운 것 / 수치 변화*를 남긴다.

> README에 AI 활용 사실과 참고한 기존 도구(CyberChef "Magic", Ciphey, Katana, curl, binwalk, zsteg, jwt_tool,
> pwntools, pwninit, checksec, radare2, RsaCtfTool 등)를 명시한다. 코드는 가져다 쓰지 않는다.

## 9. 알려진 한계

- **`auto` 가 못 푸는 것:** base62, base45, uuencode, 아핀 암호, 베이컨 암호, 접두사보다 긴 XOR 키, 글자 암호 세 겹 이상.
- **해결률 벤치마크는 직접 만든 문제다.** 실제 대회 문제에서의 해결률은 아직 모른다 (v0.30 의 실전 기록으로 확인한다).
- **XOR 은 글자 입력에 곧바로 시도하지 않는다.** 가짜 플래그를 막기 위한 규칙이다. 글자로 주어진 XOR 암호문은
  `codec decode xor -k` 나 `crack xor` 로 직접 풀어야 한다.
- **`start` 가 푸는 압축은 zip, tar, gzip 뿐이다.** 7z, rar, 암호 걸린 zip 은 풀지 않는다. 다른 파일 뒤에 붙은 zip 은
  풀지 않고 `triage` 가 안을 들여다본다.
- **`start` 는 50MB 가 넘는 파일을 분석하지 않는다.** 목록에만 적는다.
- **외부 도구의 출력 형식은 버전마다 다르다.** binwalk v3, checksec.sh 와 pwntools 의 checksec 처럼 형식이 다르면
  일부 항목을 추리지 못할 수 있다(오류 없이 빠질 뿐이다). 진짜 도구로는 `file` 만 확인했다.
- **binwalk 는 탐지만 한다.** 추출은 하지 않는다.
- **기본값은 드림핵에 맞춰져 있다.** 다른 대회는 대회 폴더에서 `ctfkit config` 로 바꾼다.
- **대회 설정은 작업 폴더 밖에 있는 것만 읽는다.** 작업 폴더를 거치지 않고 문제 파일을 직접 푼 폴더에서 실행하면,
  그 안의 `.ctfkit.json` 을 구분하지 못한다. `config show` 로 어느 파일을 읽는지 확인할 수 있다.
- **짧은 비즈네르 암호문:** 75바이트 안팎까지 1순위로 복구한다. 더 짧거나 키가 길면 일부 글자가 틀릴 수 있다.
- **XOR 다중 바이트 키:** 대략 데이터 길이의 1/50 길이 키까지 안정적이다.
- **점수 함수의 임계값**(`SOLVED_THRESHOLD` 등)은 예제로 맞춘 값이다.
- **토큰은 추정값이다.** UTF-8 바이트 수 / 4.
- **`web`:** 허용 호스트 목록 밖으로는 요청을 보내지 않고, 반복 요청에 속도 제한과 총량 상한을 둔다.
- **`rev`·`pwn`:** 로컬 파일 정적 분석과 오프셋·가젯 계산, 스크립트 초안 생성까지.

## 10. 보류 (이번 마감 범위 밖)

마감 뒤에 다시 볼 수 있게 적어 둔다.

- **개인 지식 창고:** 풀면서 쓴 페이로드·스크립트·메모를 검색할 수 있게 쌓기. 실전 도구로서 가장 가치가 커지는 부분이지만
  쌓을 내용이 먼저 있어야 한다
- 레시피(파이프라인): `auto` 가 찾은 경로를 다른 입력에 다시 쓰기
- RSA 공격 자동 선택: 작은 e 세제곱근, Hastad, 여러 n 의 공통 인수, Pollard p-1
- 스테가노 심화: PNG 청크 검사(IEND 뒤 데이터, 높이 변조), LSB 조합 전수 탐색
- 치환 암호 풀이 (쿼드그램 + 대용량 코퍼스 필요)
- MCP 서버 (argparse 스키마에서 에이전트용 도구 목록 자동 생성)
- 실제 에이전트로 토큰·시간 측정 (이전 로드맵의 v0.25)
- `auto` 탐색 과정 트리 출력
- PyPI 배포
