# 벤치마크: ctfkit 은 AI 에이전트의 토큰과 시간을 얼마나 줄이는가

AI 에이전트(Claude Code 등)가 CTF 문제를 풀 때 드는 비용은 세 가지다.

1. **호출 수**: 명령을 한 번 실행할 때마다 모델이 결과를 읽고 다음 행동을 정한다. 왕복이 늘수록 느리고 비싸다.
2. **작성 토큰**: 에이전트가 직접 써야 하는 명령과 코드. 모델이 생성하는 쪽이라 읽는 것보다 느리고 비싸다.
3. **읽기 토큰**: 에이전트가 읽어야 하는 명령 결과.

이 벤치마크는 같은 과제를 두 방법으로 풀어 위 값을 비교한다.

| 방법 | 내용 |
| --- | --- |
| 표준 라이브러리 | 파이썬 표준 라이브러리만으로 푸는 코드. 에이전트가 도구 없이 직접 짜는 경우를 가정한다 |
| ctfkit | `ctfkit -q <명령>` |

> 이 문서는 토큰·시간 벤치마크(`run.py`)를 설명한다. 해결률 벤치마크(`solve.py`)는 맨 아래 "해결률 벤치마크" 절에 있다.

## 실행

```bash
python bench/run.py              # 표를 화면에 출력
python bench/run.py --write      # bench/RESULTS.md 와 bench/history/v<버전>.md 로 저장
python bench/run.py --repeat 5   # 실행 시간을 5번 재서 중앙값 사용
```

외부 패키지나 API 키가 필요 없다. 문제 파일은 실행할 때 임시 폴더에 만들고, 난수 시드를 고정해 매번 같은 문제가 나온다.
최신 결과는 [RESULTS.md](RESULTS.md), 버전별 기록은 [history/](history/) 에 있다.

## 과제 (14개)

과제 정의는 [tasks.py](tasks.py) 에 있다. 인코딩(한 겹·세 겹·다섯 겹), 고전 암호(시저·비즈네르·XOR),
큰 바이너리에서 플래그 찾기, JWT 변조, RSA(가까운 소인수·비너), 파일 뒤에 붙은 ZIP(플래그 그대로 / Base64 메모),
해시 사전 공격, cyclic 오프셋.

두 방법 모두 마지막 명령의 출력에 정답이 있어야 한다. `tests/test_bench.py` 가 이를 검사하므로,
어느 한쪽이 답을 못 내는 과제는 표에 올라가지 않는다.

## 측정 규칙

- **호출 수**: 실행한 명령의 개수.
- **작성 토큰**: 실행한 명령 문자열 전체. 여러 줄 코드는 heredoc 으로 넘긴다고 보고 코드 전체를 센다.
  앞 단계의 출력을 다음 명령에 붙여 넣는 경우 그 글자도 포함한다.
- **읽기 토큰**: 모든 단계의 stdout + stderr.
- **토큰 수**: UTF-8 바이트 수를 4로 나눈 추정값이다. 실제 토크나이저 결과와 다르다.
- **실행 시간**: 명령이 도는 시간만 잰다. 모델이 생각하고 글자를 생성하는 시간은 포함하지 않는다.

## 비교 대상을 어떻게 정했나

비교 대상을 일부러 비효율적으로 짜면 숫자는 좋아지지만 의미가 없다. 다음 기준을 지킨다.

- 표준 라이브러리 코드는 플래그 형식(`DH{...}`)을 알고 있다고 보고, 그것으로 걸러서 필요한 줄만 출력한다.
- 코드는 줄바꿈과 변수 이름을 줄여 짧게 쓴다.
- 풀이 방법을 미리 안다고 가정한다 (예: RSA 과제에서 처음부터 페르마 분해 코드를 쓴다).
  실제 에이전트는 방법을 찾는 데 왕복이 더 들기 때문에, 이 가정은 표준 라이브러리 쪽에 유리하다.
- 여러 겹 인코딩은 한 번에 한 겹씩 벗긴다고 가정한다. 안쪽 겹은 벗겨 봐야 알 수 있기 때문이다.

## 한계

- **표준 라이브러리만 비교한다.** pwntools, RsaCtfTool 같은 전문 도구가 설치돼 있으면 비교 대상의 코드가
  훨씬 짧아진다. 이 벤치마크는 "아무것도 설치되지 않은 환경" 을 기준으로 한다.
- **토큰은 추정값이다.** 한글이 많은 출력은 실제 토큰 수와 차이가 더 크다.
- **모델 비용을 직접 재지 않는다.** 실제 에이전트가 쓰는 토큰에는 시스템 프롬프트, 이전 대화, 생각하는 과정이
  포함된다. 호출 수가 줄면 이 비용도 함께 줄지만, 이 벤치마크의 숫자에는 들어 있지 않다.
  실제 에이전트로 잰 사례는 ROADMAP 의 v0.25 에서 따로 기록한다.
- **과제 선정이 결과를 좌우한다.** 과제 13개는 직접 고른 것이라 대표성이 완전하지 않다.
  ctfkit 이 불리하거나 차이가 없는 과제도 빼지 않고 표에 남긴다.

## 명령을 찾는 비용

과제 표는 "어떤 명령을 쓸지 이미 안다" 고 가정한다. 처음 보는 도구에서는 그 전에 명령을 찾는 비용이 든다.
`run.py` 는 과제에 쓰인 (명령, 하위 명령) 을 모아 두 방법의 비용을 따로 잰다.

- **`-h` 를 따라 내려가기:** `ctfkit -h` 한 번, 명령마다 `ctfkit CMD -h`, 하위 명령마다 `ctfkit CMD SUB -h`.
- **`ctfkit guide` 한 번.**

실제 에이전트는 필요한 `-h` 만 골라 읽으므로 앞의 값은 상한에 가깝다. 또 guide 는 주요 옵션만 담고 있어,
드문 옵션이 필요하면 `-h` 를 추가로 읽어야 한다. 이 표는 과제 표의 합계에 더하지 않고 따로 보고한다.

## 과제와 비교 코드의 변경 기록

과제나 비교 코드를 바꾸면 이전 버전의 수치와 직접 비교할 수 없다. 바꾼 내용을 여기에 적는다.

| 버전 | 변경 | 영향 |
| --- | --- | --- |
| v0.23 | "파일 뒤 ZIP" 비교 코드가 ZIP 내용 전체를 출력하던 것을 플래그만 걸러 출력하도록 수정. "비교 코드는 플래그 형식으로 걸러 출력한다" 는 규칙을 이 과제만 어기고 있었다 | 표준 라이브러리 읽기 토큰 337 → 194. ctfkit 에 불리한 방향 |
| v0.23 | 과제 "PNG 뒤 ZIP 안의 Base64 메모" 추가 (13개 → 14개). 내용을 봐야 다음 단계를 알 수 있는 파일 분석 과제가 없었다 | 표준 라이브러리 호출 수 +2 |

v0.22 이전 수치와 비교할 때는 [history/](history/) 의 표가 당시 과제·비교 코드 기준이라는 점에 주의한다.

## 해결률 벤치마크 (`solve.py`)

토큰·시간 벤치마크는 "풀 수 있는 문제를 얼마나 싸게 푸는가" 를 잰다. 해결률 벤치마크는 그 앞의 질문인
"**얼마나 푸는가**" 를 잰다. v0.24 까지 이것을 재지 않아서, 흔한 인코딩 대부분을 못 푼다는 사실이 수치에 드러나지 않았다.

```bash
python bench/solve.py              # 표를 화면에 출력
python bench/solve.py --write      # bench/SOLVE.md 와 bench/history/solve-v<버전>.md 로 저장
python bench/solve.py --failures   # 못 푼 문제와 오탐의 입력을 함께 출력
```

### 문제

- **한 겹 215문제:** 인코딩·암호 43종마다 무작위 플래그 5개.
- **두 겹 100문제, 세 겹 60문제:** 결과가 글자라 겹쳐 쓸 수 있는 13종을 무작위로 조합.
- **플래그가 없는 입력 72개:** 평문 문장, 문장의 base64, 무작위 바이트의 hex·base64, 무작위 기호 글자열, 무작위 숫자 목록.

### 규칙

- **문제는 ctfkit 코드를 쓰지 않고 만든다.** 인코더를 `solve.py` 안에 표준 라이브러리로 따로 구현했다.
  ctfkit 의 `encode` 로 만든 문제를 ctfkit 의 `decode` 로 풀면 같은 버그가 양쪽에 있어도 통과한다.
- **맨 위 결과의 플래그가 정확히 같아야 정답이다.** 후보 목록 어딘가에 있는 것은 정답으로 치지 않는다.
  대소문자·기호를 잃는 세 종류(모스 부호, A1Z26, 베이컨 암호)만 상위 3개 안에서 글자가 맞으면 정답으로 본다.
- **지원하지 않는 인코딩도 넣는다.** base62, base45, uuencode, 아핀 암호, 베이컨 암호는 구현 계획이 없지만 표에 남긴다.
- **플래그가 없는 입력에서 플래그를 찾았다고 하면 오탐이다.** 변환을 늘리면 우연히 플래그 모양이 된 쓰레기가 나오기 쉬워진다.
  해결률만 보면 이 부작용이 보이지 않아서 따로 센다.
- **시드를 고정한다.** 실행할 때마다 같은 문제가 나온다.

### 한계

- **직접 만든 문제다.** 실제 대회 문제가 아니고, 인코딩 목록과 겹치는 방식을 직접 골랐다.
  실제 문제는 인코딩 사이에 설명 글이 섞이거나, 일부만 인코딩돼 있거나, 플래그 형식이 다르다.
- **플래그가 `DH{영단어_영단어}` 꼴이다.** 고전 암호의 키 추정은 영어 빈도에 기대므로, 무작위 글자로 된 플래그에서는 더 어렵다.
- **문제를 만든 사람이 도구도 만든다.** 못 푸는 종류를 일부러 넣어 두었지만, 무엇을 넣고 뺄지 정한 것은 같은 사람이다.
- **오탐 입력 72개는 적다.** 0개가 나왔다고 오탐이 없다는 뜻은 아니다.

## 에이전트 벤치마크 (`agent.py`)

`run.py` 는 에이전트가 짤 코드를 가정해서 센다. `agent.py` 는 실제 Claude Code 를 `claude -p --output-format stream-json` 으로 돌려
마지막 결과의 토큰·비용·왕복 수와 도구 호출 기록을 받는다. **실행한 사람의 Claude 사용량을 쓴다.**

- 조건 A: ctfkit 이 없는 가상환경의 python 을 PATH 맨 앞에 두고, ctfkit 실행 파일이 있는 폴더를 PATH 에서 뺀다. 지시문에서도 쓰지 말라고 한다.
  셸 명령 기록에 ctfkit 실행이 있으면 그 실행은 무효다 (경로 안의 글자는 세지 않는다).
- 조건 B: "`ctfkit start chall` 로 시작하고, 플래그가 없으면 AGENTS.md 를 읽어라".
- 정답: 답의 마지막 줄에 플래그가 있어야 한다. 모의 문제 파일에는 플래그가 그대로 들어 있지 않다 (테스트가 검사).
- 실행마다 `--budget`(USD) 과 `--timeout`(초) 상한을 건다. MCP 서버는 끄고(`--strict-mcp-config`), 도구는 Bash·Read·Write·Edit·Glob·Grep 만 준다.
- 결과는 `agent_results.jsonl` 에 한 줄씩 쌓이고, `AGENT.md` 는 그 기록으로 다시 만든다 (`--report`).
  `--round 이름` 으로 측정 회차를 나누고, 중단된 측정은 `--resume` 으로 이어서 한다. 기록에서 로컬 경로는 가린다.
- 실제 워게임 문제는 git 이 무시하는 `bench/real/` 에서 읽는다. `이름.zip` + `이름.flag`(정답 한 줄), 또는 `이름/` 폴더 + `이름/flag.txt`.
  선택으로 `이름.note` 에 보고서용 짧은 설명을 쓴다. 정답 파일이 없는 문제(서버가 있어야 하는 문제 등)는 건너뛴다.
  기록에는 수치만 남는다: 문제 id 는 이름의 해시, 도구 호출은 도구 이름과 ctfkit 사용 여부뿐이다. 정답 파일 쪽 경로를 건드린 실행은 무효다.

### 실행 기록 분석 (`agent_logs.py`)

`python bench/agent_logs.py <--workdir 폴더>` 는 실행마다 남은 `stream.jsonl` 에서 도구 호출을 분류하고, 결과 크기 × 이후 다시 읽힌 횟수로
재읽기 비중을, 오류 난 호출을 원인별로 센다 (명령 내용·플래그는 출력하지 않음). 11/24 에 지금까지의 기록을 분석한 결과:

- **비용은 왕복 수가 정한다.** 왕복마다 쌓인 대화(약 8~9천 토큰)를 다시 읽는다. 비용은 캐시 쓰기 40~58%, 캐시 읽기 22~30%, 출력 20~32%.
- **ctfkit 과 관계없는 헛걸음이 컸다.** 실제 문제에서 오류 난 호출이 실행당 A 1.56번, B 1.44번. 콘솔 인코딩(cp949) A 0.78·B 0.44,
  `python3` 이 윈도우 Store 껍데기라 실패 A 0.33, 모의 문제 A 는 `strings` 없음 0.20·`python3` 0.20.
  즉 모의 문제의 절감 일부는 **윈도우에서 A 가 겪은 환경 문제** 덕이다. 리눅스였다면 차이가 더 작았을 것이다.
- **에이전트는 start 출력을 읽고 AGENTS.md 를 또 연다.** 실제 문제 B 는 9번 모두 그랬고, 재읽기의 58% 가 AGENTS.md(와 함께 연 원본 파일)였다.
- 모의 문제 B 에서 플래그를 찾은 경우 재읽기의 82% 가 start 출력(약 1,170자)이다.

이를 보고 두 가지를 고쳤다: 에이전트 셸이면 start 가 AGENTS.md 를 바로 출력하고, AGENTS.md 에 실행 환경(python 명령, `-X utf8`,
없는 도구의 ctfkit 대체 명령)을 적는다. 둘 다 문제의 트릭과 관계없는 수정이다 (ROADMAP 6.1).

### 측정 규칙: 개발용과 평가용을 나눈다

측정에서 못 푼 문제를 보고 고친 뒤 같은 문제로 다시 재면, 시험 문제로 공부하고 같은 시험을 다시 보는 것과 같다 (머신러닝의
테스트 데이터 누수). 모의 문제 2차(-29%)가 그런 값이었다. 그래서 실제 문제는 두 폴더로 나눈다.

| 폴더 | 용도 | 명령 | 규칙 |
| --- | --- | --- | --- |
| `bench/real/dev/` | 개발용 | `--real` | 실패를 보고 고쳐도 된다. 여기서 잰 수치는 "고친 문제로 잰 값" 으로만 적는다 |
| `bench/real/eval/` | 평가용 | `--eval` | 고치기 전에 내용을 보지 않는다. 커밋한 깨끗한 상태에서만, 문제마다 한 번만 잰다 |

- 새 문제를 받으면 반씩 나눠 넣는다. 분야가 한쪽에 몰리지 않게 한다.
- `--eval` 은 커밋하지 않은 변경이 있으면 거부하고, 기록에 커밋을 남긴다. 평가용으로 이미 잰 문제는 `--again` 없이 다시 재지 않는다.
- 평가가 끝나면 ctfkit 이 도움이 안 된 문제(B 가 틀렸거나 B 비용이 A 이상)를 출력한다. 그 문제는 `dev/` 로 옮겨 분석하고,
